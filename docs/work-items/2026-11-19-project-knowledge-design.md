# Project Knowledge plugin design

Status: Design draft incorporating the accepted [plan challenge](2026-11-19-project-knowledge-plan-challenge.md). The November 19 brainstorm in the local project notes holds the dated product decisions. Host, upstream and refresh behavior still need qualification before release.

## Product

Give each project one knowledge store that people can inspect and an agent can query directly. The agent consults it before gathering project information with other tools, making decisions or taking actions, and giving project information to a user or subagent. It maintains durable knowledge as work happens. People can follow a current fact to its source and see what it replaced. The project can publish selected current facts to its existing documentation.

Build on the review toolkit's five-tier Markdown store and ranking engine. Reuse the bounded retrieval, source-backed evidence, freshness, and optional Git practices in Monolithic Dev Harness Epic 0005. AGE-142 covers the per-store query tool. Session archival, tracker workflows, and host-wide policy enforcement are outside this design.

## Setup and one store per project

Setup offers `Project_Knowledge` directly under the project root. The user may give a different name, location, or both. The path from the root must stay within the project and use visible folders. Validate resolved paths as well as entered paths, so a symlink or junction cannot send store writes outside the project or into a hidden folder.

For Git projects, ask whether to track the store and offer tracking as the default. Track the curated units, lineage, glossary, store tools, and flow records needed to interpret the shared store. Apply the project's sharing rules to facts, source references and flow records. Keep private material, raw diagnostics, machine and session state, locks, and temporary files local. Use lock placement that creates no hidden directory inside the store. For projects without Git, provide the same setup, retrieval, curation, and on-demand refresh using local files.

Use one project-root locator for the store. The draft proposes a visible `project-knowledge.json` with a project-relative path. The query skill, hooks, release tooling, and other consumers resolve the same locator. Store the verified interpreter path through the existing machine-local host setup. The interpreter setting carries no second store path. A mismatch between the locator and a path passed by an integration must produce a diagnostic rather than a second active store.

Upgrade reads legacy paths as migration inputs. A single existing store in a visible location can be adopted there as the project's custom location. Offer an existing store in a hidden location a migration to the default or the user's chosen visible path. If legacy settings identify multiple stores, show their locations and ask the user which one to bring forward. Copy the chosen store, verify content and lineage, and rebuild and check its catalog. Verify that incompatible legacy writers have been stopped or isolated before switching the locator. Preserve old files as an inactive recovery copy. If verification fails, keep the migration pending and explain how to retry. Never merge roots or delete legacy data as part of setup.

Setup finds and verifies a user-provided Python 3.12 or newer, including when `python3` points at an older interpreter. It reports an actionable requirement if no suitable interpreter is found. Setup creates and populates the store from verified project sources. It generates a glossary with sourced terms and aliases and a project query skill from the shared workflow, both defaulting to the language of the project's documentation. Unknown facts remain open questions. The installed tools and engine come from a pinned release, so a hook never executes a repository copy of `query.py` merely because it exists.

## Retrieval and the gate

Each store ships `query.py` with the upstream review-toolkit engine beside it. The CLI exposes `catalog`, `find`, `fetch`, `glossary`, `links`, `rebuild-catalog`, and version-checked curation. One engine serves a current fact view and an explicit historical view over the same stored units. Select current fact sections before ranking and bounded fetch. The catalog is rebuildable. Hooks invoke the installed copy of the same CLI with the configured store as its data root. Remove the knowledge MCP registration and its private Python provisioning from this product's install path when its consumers have migrated.

At session start, give the agent a brief orientation. On every user message, look up a small set of relevant snippets and remind the agent to ask its own task-specific query first. Cap the lookup time and injected size. Keep the instruction if the lookup times out or yields no context. Qualify the time budget on representative fixtures. Quote snippets as project evidence with provenance. Store content has no authority over host control, tool permissions or the query instruction. The agent uses the task to choose search terms and fetches the relevant sections. It checks primary sources when the store is stale, incomplete, or gives conflicting evidence.

The gate checks for an observed agent query on the current task, scoped to its project and agent or subagent context. A hook's automatic lookup and a catalog listing alone do not satisfy the check. An actual task search or direct fetch of the relevant unit can satisfy it. The gate verifies the call and its outcome. Task relevance and good use of the results are evaluated in behavior tests. The agent refreshes that context when the task changes.

Where the host can intercept a project read, search, edit, or handoff, require the query first. Explain which query to run and why it helps. Always let the retrieval command run. On an empty store, no useful match, stale results, or an unavailable store or interpreter, allow work to continue with focused source reads. Apply the same instruction before project answers. Enforce the order at the response boundary only where a supported host event can reliably steer the agent before delivery. Loops and retries must end after a query attempt or an observed fallback condition. This gate leaves host permissions and project approval rules in force.

| Host | Proposed route | Check before claiming coverage |
| --- | --- | --- |
| Claude Code | Session and prompt events for orientation and snippets. Tool hooks for covered reads, searches, edits, and handoffs. | Verify the actual matchers and agent-visible explanation in the installed host. Separate local Claude Code from Cowork or cloud results. |
| Codex | Session and prompt events for context. Tool hooks for supported shell, patch, and other local tools. | Confirm trust and tool coverage on the installed CLI and Desktop. UPF's current portable adapter has no generic file-read matcher for Codex. |
| Cursor | Session-start context and documented tool interception. | Verify whether the installed Agent can receive per-message context before the first model call. The documented submit hook schema reviewed here provides a submit decision and a user message. Report the gap if the tested host lacks context injection there. |

Use existing host adapters to translate events. Keep the query policy the same across hosts. For each client and action, document context delivery, observed query outcomes, enforced tool order and instructions-only coverage separately. If a host lacks a required hook, retain the query skill and instruction, report the gap in setup, and resolve the unsupported requirement before claiming full support. The extra injection points for file edits, plans, and handoffs can wait until qualification shows a specific context gap. ## Curation and refresh

The agent decides what durable, sourced knowledge belongs in the store. Facts from people remain owned by the authoritative project docs. The store owns curated derived findings. Keep provenance, source locators and fingerprints, and the event that produced each fact. Preserve uncertainty explicitly.

Keep one stable fact ID and an ordered set of revisions within the same unit. When a fact changes, preserve the original text, mark its revision obsolete or deprecated, and insert the replacement immediately after it. Search and injection surface current facts by default. Explicit history retrieval shows both with their sources and statuses. Import legacy units without rewriting their text. Use the existing IDs for legacy entries where possible. Split independently changing facts as the agent encounters them, preserving the migrated text as evidence.

All writes pass through one validation contract, including refresh and doc ingestion. The upstream engine owns underlying locking and atomic file replacement. The curation layer owns the right to write and the rules for status changes and new revisions. Engine-level whole-file writes remain internal. Concurrent edits use expected versions and surface a conflict when the target changed. Serialize managed writes to the catalog and flow log, even when writers update different units. Resolve managed lock identity from the same physical store across supported path spellings. For tracked stores, validate one current revision per fact and preservation of earlier text across proposed Git changes. If two branches produce competing successors, the agent reconciles them against their sources and retains both contributions in history. Ordinary curation has no delete operation. An exceptional deletion needs direct user approval for the exact fact, revision and scope. Removing data from the active store, Git history or external copies are distinct scopes.

The agent records durable findings when it identifies them during work. The end-of-session check handles identified but outstanding findings. Use an earlier supported checkpoint if a host cannot steer the agent during shutdown, and keep any pending entries available at resume rather than assuming the session finished cleanly. Manual refresh works with current source fingerprints even without Git.

Each update to the default branch triggers refresh, including merges and direct pushes. GitHub Actions is the initial proposed hosting adapter. Separate observed events, pending curation and completed refresh. Persist a handoff containing bounded source-change metadata that a later agent can recover after the originating runner exits. Qualify whether provider artifacts and local reconciliation provide enough durability before adding a separate service. A local-only store catches up when its environment can next observe the branch. Use the last completed revision and current sources to recover when delivery was missed, canceled or expired. [GitHub Actions push events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#push).

Use a changed revision or source snapshot to find the affected facts. Match changed, renamed or missing paths against normalized sources. Reconcile available events in source order and keep the completed revision from moving backwards when an old event arrives late. After a missed event or rewritten branch, use a source snapshot and label catch-up when intermediate events cannot be reconstructed. Source change makes a fact potentially stale. Missing or unverifiable evidence remains visible as unverified and prevents automatic publication of that fact. A store-only change with no affected sources completes as a no-op and creates no follow-up commit. The agent verifies affected facts and records replacements where warranted. Findings about work in progress stay out of default-branch publication until verified there. Replays preserve pending work, and refresh reports completion only after the affected facts are accounted for. Analysis jobs have no implicit permission to push, auto-merge, or publish externally.

## Documentation flow

Each fact has one owner and a permitted direction. `ingest-docs` quotes people-owned passages into `stated` facts. `publish-docs` writes selected current store-owned facts to explicit destinations in existing docs. The marker in a destination document is the mapping. It gives the region a stable ID and lists the store fact IDs it accepts. The region's body carries generated text with stable fact boundaries. Treat its marker and body as a checked snapshot. Duplicate IDs, malformed boundaries, a missing destination, or an unmapped fact produce a diagnostic and skip that region.

Keep an append-only flow log in the store. Record direction, source and destination, fact and revision IDs, origin, event, time, and fingerprints. Ingestion skips generated spans. Publication verifies ownership, the mapping, current values, and the last published fingerprints. It writes inside its verified regions only. Internal writes use a lock and recheck versions at the write boundary.

A change outside the logged flow is an external edit. A fingerprint shows that the bytes changed. It cannot establish a person's identity. Treat coherent edited facts as people-owned without crediting an unverified author. Freeze their publication and let ingestion bring the edited facts back into the store with their provenance and history. Unchanged generated spans remain excluded. If the changed text cannot be mapped cleanly to a fact, freeze the affected region and report the ambiguity. Resume publication only after the ownership or placement is resolved.

Use a checked patch as the ordinary publication route for editable docs. Bind it to the source fact revisions, region mapping and destination version, and recheck all three when applying. A changed marker freezes routing for that region until resolved. Enable direct automatic apply only for a destination with verified isolation or equivalent write protection. Plugin locks coordinate managed writers. An unrelated editor may save between the final check and file replacement.

Record the intent for a doc or store write before changing the target, including the expected and intended fingerprints. Record completion after verifying the new target. On retry, matching the intended fingerprint finishes the existing flow record. Matching the expected fingerprint permits a retry if the source revision and mapping are still valid. Any other fingerprint is an external conflict and preserves the changed text. An index rebuild is repeatable and can recover after the underlying unit write succeeds. Use the same recovery behavior in both directions.

## Builder and failure-case checks

| Scenario | Acceptance evidence to collect |
| --- | --- |
| Fresh Git and non-Git projects, plus an existing hidden store | Setup offers the visible default, validates custom paths, asks about Git tracking for Git projects, and migrates only the selected store. An interrupted migration leaves the previous data available. |
| A message gets injected hits and the agent then starts a project action | The trace shows automatic context, a separate agent query based on the task, and subsequent tool use or a reasoned fallback. Cover direct project answers and subagent work separately. |
| Store empty, stale, missing, corrupt, or inaccessible | Each qualified host continues with a focused source check. The gate explains recovery where it can intercept the action, and never loops. |
| Changes land quickly, events repeat, or the branch is rewritten | Refresh covers all changed sources, leaves unrelated facts alone, and catches up after missed events. It preserves fact history and marks unverifiable facts for follow-up. |
| A fact changes or two writers start from the same version | The original text remains directly before its successor. A query matching only obsolete text yields no current hit or snippet. Default fetch excludes historical text, and explicit history returns it. A stale write gets a conflict. A text merge with competing successors is rejected until reconciled. |
| Someone edits one fact in a published region or a write is interrupted | A detected edit is preserved and its ownership change is traceable. Unchanged generated facts do not flow back. Resume after any write step without duplicating an update. An external edit visible at a version check stops the write, and publication uses a qualified destination for concurrent edits. |
| Native Windows on Python 3.12 or newer | The pinned upstream engine loads and queries work. Competing writers report a conflict. Test interrupted writes and catalog recovery as well as the happy path. Qualify desktop hooks separately. |

## Delivery and qualification

The [implementation and qualification plan](2026-11-19-project-knowledge-implementation-plan.md) sequences the work and proposes how to reconcile AGE-142 with this design.

Qualify a pinned upstream revision on Linux, macOS, and native Windows. Its locking must work without hidden folders inside the store and its retrieval must support the current fact view before ranking or fetching. Consume the released revision unchanged. Deliver and verify setup, query, curation, and migration as a testable slice. Then verify host retrieval and refresh adapters, and finally the two documentation flows with contention and recovery tests. Host qualification requires an actual session on each supported client and version in addition to adapter tests. The release also needs an end-to-end run showing a later agent recovering pending refresh work and completing it.

The [plan challenge](2026-11-19-project-knowledge-plan-challenge.md) records the accepted tradeoffs and the synthetic Linux fixture that reproduced hidden lock placement and obsolete results in the currently pinned engine. The acceptance evidence above still needs to be collected against the implementation.
