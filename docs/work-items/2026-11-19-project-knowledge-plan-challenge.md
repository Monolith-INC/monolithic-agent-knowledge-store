# Project Knowledge plan challenge

Status: Amendments accepted on 2026-11-19 and integrated into the [design](2026-11-19-project-knowledge-design.md) and [implementation plan](2026-11-19-project-knowledge-implementation-plan.md). This record distinguishes observed behavior from scenarios that still require live evidence.

## Findings that change the plan

1. **The upstream work is larger than Windows locking.** The pinned engine creates a hidden `.locks` folder on write. Its `find` filters by unit status and then indexes every section of a matching unit. Its default `fetch` returns the raw unit. In a temporary store using the shipped engine on Linux and Python 3.12.13, an obsolete-only term returned the obsolete section of a current unit, a default fetch included that text, and one write created `.locks`. Keep historical text next to its successor as agreed. Qualify an upstream revision that supports visible or machine-local lock placement and can rank the current fact view with the same search engine. History remains available through an explicit read. A post-search filter alone can let old sections use up the result budget and crowd out current facts. [Pinned engine search](../../runtimes/project-knowledge/vendor/review-knowledge/adapters/knowledge/knowledge_store.py#L519), [fetch](../../runtimes/project-knowledge/vendor/review-knowledge/adapters/knowledge/knowledge_store.py#L635), [writer](../../runtimes/project-knowledge/vendor/review-knowledge/adapters/knowledge/knowledge_store.py#L789).
2. **Default-branch refresh lacks a proven handoff.** A push can trigger a run, but a run that finds stale facts has not updated the store. The plan does not specify how the next agent receives pending work after the run ends. UPF's existing CI also cancels superseded runs, so reusing its workflow unchanged could drop refresh work. Require a durable handoff for a tracked store and a local reconciliation path for missed events or local-only stores. Treat observed revision, pending curation, and completed refresh as distinct states. [UPF CI](../../.github/workflows/ci.yml#L3), [GitHub concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency), [workflow artifacts](https://docs.github.com/en/actions/concepts/workflows-and-actions/workflow-artifacts).
3. **Managed locks do not protect against parallel versions in Git or legacy writers.** Two checkouts can each accept a valid successor for the same fact. A text merge can leave two current revisions or discard history even though both writes passed. The active-store switch also needs evidence that legacy readers and writers have moved. Validate store lineage across tracked changes. Treat concurrent successors as a conflict for the agent to reconcile against the sources. Keep format migration reversible and verify that an old client cannot keep writing to the recovery copy as if it were active. [Managed writer](../../runtimes/project-knowledge/vendor/review-knowledge/adapters/knowledge/knowledge_store.py#L789), [legacy setup writer](../../packages/cli/src/tooling-runtime.ts#L134).
4. **Hook delivery, query observation, and useful retrieval are separate promises.** A host may deliver prompt context without exposing all project reads. A before-tool event may enforce a query before a shell call while leaving an answer without tools to the agent's instructions. The observed query proves execution and outcome. Relevance and grounded use need their own behavioral checks. Make coverage a per-host, per-surface result. Set a deadline for injection, measure the cost of the additional query, and preserve the active-query instruction when injection yields no context. [Codex tool coverage](https://learn.chatgpt.com/docs/hooks#tool-coverage), [Claude Code hooks](https://code.claude.com/docs/en/hooks), [Cursor hooks](https://cursor.com/docs/hooks).
5. **Publishing needs a safe default and a versioned handoff.** A whole-file replacement can race an unrelated editor. Even a reviewed patch can become stale before application. Start with a patch for ordinary editable documents. Bind it to the source fact revision, destination version and region mapping, and recheck them when applying. Enable direct writes only for a destination with verified isolation or equivalent protection. A changed marker has to be treated as a changed routing contract before publication resumes.

## 1. Assumption Audit

Confidence refers to the assumption as stated today. Impact describes what changes if it fails.

| Assumption | Confidence and impact | Stress test and decision |
| --- | --- | --- |
| Changing `fcntl` alone makes the current engine suitable to ship unchanged. | Contradicted. High impact on upstream scope. | The fixture reproduced hidden lock placement and obsolete hits. Qualify lock behavior, location and current-only retrieval together before pinning a release. [Python 3.12 module availability](https://docs.python.org/3.12/library/fcntl.html). |
| Each supported host can supply message-time snippets and require a separate query before project tools or answers. | Low across all surfaces. High impact on the user promise. | Test a turn with a file read, a direct project answer with no tools, a mixed shell action, and a subagent in each actual client. Include untrusted or disabled hooks. Publish the coverage matrix. Bring a missing required surface back for a scope decision. |
| A default-branch update can trigger work that survives the runner and reaches a later agent. | Low for the handoff. High impact on freshness. | From one environment, merge and push with no agent active. From a fresh checkout, recover the pending work without the first runner, process it, then replay the same event. Test retention expiry and canceled or out-of-order events. |
| Source references are precise enough to refresh selected facts. | Medium. High impact on correctness. | Test an exact file, a directory source, a rename, an external source and a missing original. Normalize repository paths and pin the observed revision. Unresolvable evidence marks a fact unverified and keeps it out of automatic publication. |
| A checked copy and selector change are sufficient for migration. | Low with old clients active. High impact on split writes. | Leave an old client running and try to write through it before and after migration. Require retirement or isolation of incompatible writers before switching the active locator. |
| Registered document regions and fingerprints establish that a change is safe and authored by a person. | Low. High impact on ownership and data loss. | Edit one fact, remove a marker, and change the destination during recovery. A fingerprint establishes a change. Keep the external statement and its provenance, check ownership, and freeze ambiguous publication. |

## 2. Pre-mortem Analysis

Imagine that a month after rollout the team has stopped trusting the store. It returns the old build instructions beside the new ones, blocks a trivial follow-up, appears current after a canceled refresh, and occasionally overwrites a manually corrected doc. A teammate upgraded and kept an old client, so two paths now receive updates. The team disables the hook and stops curating.

Work backward from that failure. Make the active revision obvious in search and fetch. Show when a fact was verified and whether refresh is pending. Measure actual query use, extra interventions and added time on both project tasks and ordinary chat. Test a project with no store and a deliberate query miss. Prove the old writer has stopped before migration is reported complete. Require publication to stop on a stale destination or unresolved ownership conflict. These checks describe the experience a team would notice within its first week.

## 3. Failure Mode Analysis and Boundary & Edge Case Sweep

| Boundary | Failure and observable impact | Required behavior and evidence |
| --- | --- | --- |
| Inputs and path resolution | Empty custom path, hidden ancestor, escaping symlink or junction, or an existing non-store target. Setup selects a wrong root or alters unrelated files. | Recheck resolved destination at the write boundary. Test a valid visible custom path with spaces, each rejected path, and a preexisting destination. Leave the source and target untouched on rejection. |
| Query and status | Empty, corrupt, oversized or outdated store. The hook waits too long or a stale hit is treated as current. A valid-looking query from a previous task satisfies the wrong gate. | Bound time and injected size. Keep fallbacks local to the current project, task and agent. Test cross-task and cross-worktree context, manual history reads, no matches, and an unavailable interpreter. Check that a prompt made of ordinary conversation does not receive a tool-order interruption. |
| Managed write and catalog | Store update succeeds but catalog or receipt write fails. Two writers on different units race the catalog. | Recover from actual unit contents, rebuild a deterministic catalog, and finish or retry the existing operation. Assert two independent updates both appear and retries do not duplicate history. |
| Git merge and branch change | Competing successors merge cleanly as text. An older event arrives late, or a merge and revert collapse into the same final diff. A store-only commit could retrigger its own update indefinitely. | Validate one current revision and retained history on a proposed tracked change. Key refresh to the intended project, branch and source revision. Never move the completed checkpoint backwards. Use observed change ranges or source fingerprints when events are missing. Label snapshot catch-up when an intermediate event cannot be reconstructed. Record a no-op when there are no affected sources so store-only commits do not create a feedback loop. |
| Capture and publication | A session closes before the catch-up hook can steer the agent, or `publish-docs` runs against a changed marker or source fact. | Persist identified pending work before exit. Resume without re-scanning or replaying the session. Verify source revision, region mapping, and destination version before applying. Keep conflicting external text and generated content distinguishable. |

**Cascading failure walkthrough.** Revision A arrives on the default branch and starts a refresh. Revision B cancels that run after affected facts were found but before they were handed off. A local agent next sees B and a stale fact, and someone edits its published paragraph while an earlier publication intent is pending. With the current draft, the pending work may exist only in the canceled runner, an old query hit can steer the agent, and a retry can try to apply an obsolete patch. With the proposed changes, the agent compares the current branch to its completed checkpoint, marks affected facts pending, and checks their sources before publication. The earlier patch fails its revision or destination check. The external change survives and the prior intent is recorded as conflicted. Once the agent resolves the fact, a fresh patch can be prepared. Test the entire sequence on one fixture and assert the final fact lineage, document text, checkpoint and flow log.

## 4. Security Audit Personas

| Viewpoint | Concern | Proposed release check |
| --- | --- | --- |
| Repository contributor | Knowledge snippets, a replaced in-store executable, or a changed marker could influence the agent or change what gets written. | Hooks use the pinned installed CLI. Treat snippets as quoted evidence with provenance and no control authority. A store path or marker cannot grant a tool write permission. Check that changed routing, out-of-project targets and untrusted content do not produce a write or change the gate's behavior. |
| Maintainer operating the tool | Default Git tracking can share private findings, local transcript paths, or contents embedded in logs and conflict reports. Case and path differences can split locks on Windows. | Apply the project's sharing rules to facts and source references, omitting private content and diagnostics from tracked output. Test a shareable fact next to a sensitive note. Verify the same physical store receives the same lock identity across path spellings and managed clients. |
| Auditor investigating a history change | A config edit, user claim embedded in a document, old writer, or stale approval could cause deletion or silent replacement. Git can retain copies after local removal. | Ordinary tools offer no delete operation. An exceptional deletion proposal names the exact fact, revision and affected scope. Verify direct user approval for that scope at execution. Treat deletion from the active store and removal from Git history or other copies as separate decisions. Verify unauthorized and stale proposals leave history intact. |

## Accepted architecture decisions

| Decision | Alternatives considered | Accepted choice and tradeoff |
| --- | --- | --- |
| Use one engine for current and historical reads. | Rank the entire file and drop obsolete hits afterward, create a second maintained current store, or project the current facts before handing them to the shared ranker. | Qualify a current view before ranking and fetching through the shared engine. Keep the original bytes and adjacent revisions together. This keeps one authoritative history and makes the upstream interface a first-phase dependency. |
| Separate branch-event delivery from completed curation. | Rely on runner completion, provision an unattended agent everywhere, or hand off bounded source-change metadata and reconcile locally. | Qualify a durable handoff plus local catch-up. A trusted agent session curates the facts. Expose pending as a separate state. This keeps offline and Git-free projects usable while requiring an explicit handoff for hosted repositories. Test whether provider artifacts with local reconciliation meet the need before adding another persistent service. |
| Publish editable docs through checked patches first. | Always replace in place, require users to stop editing around every publish, or bind publication to a checked destination version and apply automatically only with verified protection. | Use checked patches as the ordinary route. Enable automatic apply on qualified destinations. This preserves the tool's ability to update docs and gives it a defined safe behavior during concurrent edits. |

The revised plan applies findings 1 and 2 to phase 0, findings 3 and 5 to curation, cutover and publication, and finding 4 to host qualification and release claims. The review ran a synthetic Linux fixture against the currently pinned engine. Native Windows, installed desktop hooks and hosted default-branch refresh still require live evidence.
